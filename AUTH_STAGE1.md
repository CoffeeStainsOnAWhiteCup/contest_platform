> Исторический документ первого этапа. Актуальное состояние: [README](README.md), [сессии и GitHub OAuth](docs/AUTH_SESSIONS.md), [рейтинг, профиль и Telegram](docs/BACKEND_API.md).

Этот документ фиксирует состояние на первом этапе разработки. Актуальные настройки, хеширование и проверки описаны в [инструкции запуска](README.md).


Основа: main, коммит 01a24b56b7c0b94efb083602ab48f550cc7b740d.
Модели БД не изменяются, существующая база сохраняется.

## Что реализовано

| Метод | Путь | Результат |
|---|---|---|
| POST | /api/v1/auth/register | 201, профиль нового участника |
| POST | /api/v1/auth/login | 200, access_token, token_type, expires_in |
| GET | /api/v1/users/me | 200, профиль пользователя по Bearer JWT, путь из ТЗ |
| GET | /api/v1/auth/me | Совместимый прежний путь, deprecated в OpenAPI |

Пароль хранится как Argon2id-хеш. JWT подписывается HS256; проверяются подпись,
срок, issuer, audience, тип и UUID пользователя. Роль читается из БД.
Публичная регистрация создаёт только participant, поле role в запросе запрещено.
Дубликат email возвращает 409; неверные учётные данные и токены — 401;
недостаточные права — 403. Регистрация и вход принимают JSON.
SQL echo отключён, чтобы хеши паролей не попадали в SQL-логи.
.env исключён из Docker-образа, Compose передаёт переменные через env_file.

Параметры после сверки с TECH_SPEC(1).pdf, версия 1.0: пароль 8–128 символов,
минимум одна буква и одна десятичная цифра (FR-AUTH-03); имя 1–100 после
обрезки пробелов; регистронезависимый email; JWT на 30 минут (FR-AUTH-06).
Буквы и цифры Unicode допускаются; пароль не обрезается и не нормализуется.
Новая проверка сложности действует при регистрации, а не при входе: уже
зарегистрированные пользователи сохраняют возможность войти.
Срок меняется через JWT_ACCESS_TOKEN_MINUTES (1–1440).

## Применение патча в Windows / PowerShell

Команды вводить в терминале, а не в файлах. Перейти в папку существующего
репозитория contest_platform. Патч предназначен для указанного main.
Если main уже обновлён или git apply --check сообщает ошибку, не применять
патч принудительно: сначала адаптировать к новым изменениям.

```powershell
git status
git switch main
git switch -c feature/auth
```

До переключения рабочая папка должна быть чистой. Если feature/auth уже
существует, сначала проверить её содержимое; не удалять и не сбрасывать ветку.
Сохранить auth-stage1.patch в соседнюю папку (на уровень выше репозитория).

```powershell
git apply --check ..\auth-stage1.patch
docker compose stop api
git apply ..\auth-stage1.patch
docker compose run --rm --no-deps api python tools/init_auth_env.py
docker compose up -d --build
docker compose logs --tail=80 api
```

init_auth_env.py использует только стандартную библиотеку: можно выполнить
через старый уже собранный образ, до установки новых зависимостей. Он создаёт
случайный JWT_SECRET_KEY в локальном .env, не печатает его и не меняет настройки
PostgreSQL. Существующий непустой ключ сохраняется.
Не заменять POSTGRES_USER=user на contest_user в уже инициализированной БД.
Не использовать docker compose down -v для этой установки.

Dockerfile и зеркало установки пакетов не изменены. Если повторится ошибка
скачивания, это отдельная проблема сборки, а не JWT. Можно отдельно исправить
PIP_INDEX_URL на https://pypi.org/simple и повторить сборку.

## Проверка через Swagger UI

Открыть http://localhost:8000/docs.
POST /api/v1/auth/register, Try it out, тело:

```json
{"email":"stepan@example.com","name":"Степан","password":"StudyPass123!"}
```

Ожидается 201 и role=participant. Пароль/хеш в ответ не попадают.
Повторить регистрацию — 409. Попытка добавить role=admin — 422.

POST /api/v1/auth/login, тело:

```json
{"email":"stepan@example.com","password":"StudyPass123!"}
```

Скопировать access_token. В кнопке Authorize вставить только токен, без слова
Bearer, и подтвердить. GET /api/v1/users/me должен вернуть 200 и профиль.
После Logout в Authorize тот же запрос должен вернуть 401.
Logout здесь удаляет токен только из Swagger: серверного отзыва токена пока нет.
Не отправлять реальные токены и пароли в PR или переписку.

## Автотесты

Команды запускают временный контейнер API и устанавливают тестовые зависимости
в нём. Рабочий контейнер API от этого не меняется. Локальный Python не требуется.

```powershell
docker compose run --rm --no-deps api python tools/run_auth_tests.py unit
docker compose run --rm --no-deps api python tools/run_auth_tests.py postgres
```

Для postgres должен работать сервис db. Тест создаёт случайную схему
auth_test_<uuid> в указанной development-БД и удаляет только эту схему в конце;
таблицы приложения в public не изменяются. На production тесты не запускать.

Unit/API-тесты используют настоящий HTTP-слой, Argon2 и JWT, но подменяют
AsyncSession. PostgreSQL-тесты проверяют сохранение пользователя, вход,
нормализацию email, дубликаты и получение профиля с настоящей БД.
Исходная версия: в присланном пользователем логе подтверждены 30 unit/API-тестов
и 2 PostgreSQL-теста; Docker-сборка и регистрация/вход/профиль проверены локально.
После поправки по ТЗ: 45 unit/API-тестов проверены в среде подготовки на Python 3.11.
Обновлённые 2 PostgreSQL-теста используют /users/me и дополнительно проверяют
совместимость /auth/me. Их нужно повторить у себя; здесь PostgreSQL и Docker
недоступны. Полный набор Judge этим этапом не проверяется.

## Совместная работа с PR Judge

Этот этап создан от main и не включает PR №2. После его слияния нужно объединить
обновлённый main с feature/auth и разрешить изменения общих файлов:
app/api/deps.py, app/main.py, app/core/config.py, requirements.txt и Compose.
Сохранить все роутеры (auth, users и submissions), настройки Celery и JWT. Функции
get_current_user и require_roles имеют тот же внешний интерфейс, что в PR №2,
но X-User-Id не является способом аутентификации. Тесты submissions нужно
перевести на JWT или явно подменять зависимость текущего пользователя в тестах.

При переходе к новым моделям Judge понадобится отдельно согласовать миграцию
существующей схемы: create_all не обновляет существующие столбцы.

## Сверка с ТЗ и следующие этапы

ТЗ прочитано: TECH_SPEC(1).pdf, версия 1.0 от 02.11.2026. Матрица требований,
расхождения и последовательность работ находятся в docs/AUTH_SPEC_REVIEW.md.
Этот PR реализует базовую регистрацию, вход и получение профиля, но не весь
модуль auth/users и не полное соответствие ТЗ.

Следующий этап: rate limiting (NFR-SEC-07), refresh на 7 дней и logout с отзывом
refresh-токена (FR-AUTH-07/10). Далее GitHub OAuth, управление пользователями,
CRUD контестов/задач, рейтинг и Telegram. Блокировка должна запрещать не только
новый вход, но и использование уже выданного токена для приватных запросов.

Подтверждение email и восстановление пароля не описаны в приложенной версии
ТЗ; не включаем их в обязательный объём без отдельного расширения требований.

Противоречие ТЗ: FR-AUTH-04 допускает bcrypt или Argon2, NFR-SEC-01 требует
только bcrypt cost >= 12. Текущая реализация сохраняет Argon2id; необходимо
согласовать формулировку NFR-SEC-01 или отдельно реализовать совместимый переход.
Существующие хеши не заменять без проверки пароля пользователя.

Ограничение этапа: отсутствуют rate limiting, refresh/logout, GitHub OAuth,
блокировка/админское управление пользователями, CI/CD. /health пока подтверждает
ответ приложения, но не проверяет БД и Redis. Полное соответствие FR-AUTH-11
проверяется только после объединения с submissions и остальными приватными API.
