## Что реализовано

| Метод | Путь | Результат |
|---|---|---|
| POST | /api/v1/auth/register | 201, профиль нового участника |
| POST | /api/v1/auth/login | 200, access_token, token_type, expires_in |
| GET | /api/v1/auth/me | 200, профиль пользователя по Bearer JWT |

Пароль хранится как Argon2id-хеш. JWT подписывается HS256; проверяются подпись,
срок, issuer, audience, тип и UUID пользователя. Роль читается из БД.
Публичная регистрация создаёт только participant, поле role в запросе запрещено.
Дубликат email возвращает 409; неверные учётные данные и токены — 401;
недостаточные права — 403. Регистрация и вход принимают JSON.
SQL echo отключён, чтобы хеши паролей не попадали в SQL-логи.
.env исключён из Docker-образа, Compose передаёт переменные через env_file.

Рабочие параметры, пока не сверенные с ТЗ: пароль 8–128 символов, имя 1–100
после обрезки пробелов, регистронезависимый email, JWT на 30 минут.
Срок меняется через JWT_ACCESS_TOKEN_MINUTES (1–1440).


## Автотесты

Команды запускают временный контейнер API и устанавливают тестовые зависимости
в нём. Рабочий контейнер API от этого не меняется. Локальный Python не требуется.

```powershell
docker compose run --rm --no-deps api python tools/run_auth_tests.py unit
docker compose run --rm --no-deps api python tools/run_auth_tests.py postgres
```

## Совместная работа с PR Judge

Этот этап создан от main и не включает PR №2. После его слияния нужно объединить
обновлённый main с feature/auth и разрешить изменения общих файлов:
app/api/deps.py, app/main.py, app/core/config.py, requirements.txt и Compose.
Сохранить оба роутера (auth и submissions), настройки Celery и JWT. Функции
get_current_user и require_roles имеют тот же внешний интерфейс, что в PR №2,
но X-User-Id не является способом аутентификации. Тесты submissions нужно
перевести на JWT или явно подменять зависимость текущего пользователя в тестах.

При переходе к новым моделям Judge понадобится отдельно согласовать миграцию
существующей схемы: create_all не обновляет существующие столбцы.
