# Рейтинг, профиль и Telegram

## Запуск на текущей ветке

Команды выполняются из корня репозитория. Для существующей базы, которая уже ведётся Alembic на ревизии `6d233f26b0ba`, выполняется `alembic upgrade head`: применяются цепочки contests (`b7e4c9a1f2d3` → `c1a2b3d4e5f6`) и account-state (`a53bf892e107`), затем merge-ревизия `e4a680bb4321`. Account-state добавляет поля пользователей, счётчик версии рейтинга в контесте, журнал администрирования и очередь уведомлений. Существующие пользователи остаются активными, старые JWT и refresh-сессии читаются с версией 0.

```powershell
docker compose build
docker compose run --rm migrate
docker compose up -d
docker compose exec api python -m alembic current
docker compose exec api python -m alembic check
docker compose run --rm test sh -c 'AUTH_TEST_DATABASE_URL=$DATABASE_URL python -m pytest -q -ra'
```

Продолжайте после успешного `migrate`. Для старой базы без истории Alembic требуется отдельный перенос данных. Текущая ветка содержит merge-ревизию `e4a680bb4321`, которая объединяет цепочки contests и account-state; обновление выполняется тем же `docker compose run --rm migrate` (внутри — `alembic upgrade head`).

## Рейтинг

| Метод и путь после `/api/v1` | Ответ |
| --- | --- |
| GET `/contests/{contest_id}/leaderboard?page=1&size=20` | Страница участников одного контеста |
| GET `/rating/global?page=1&size=20` | Суммарный результат по опубликованным, активным, завершённым и архивным контестам |
| GET `/rating/me` | Глобальная строка текущего пользователя. Параметр `contest_id` выбирает доступный контест. До первой отправки возвращается `null` |
| GET `/submissions` | Существующая история отправок. Участник получает свои решения |

В таблицу контеста попадают авторы хотя бы одной отправки. Гостям и участникам доступны отдельные таблицы опубликованных и активных контестов. Judge и Admin могут открывать таблицу любого контеста. Глобальная таблица выдаёт только итоговые показатели.

Поле `place` — место, `name` — актуальное имя, `solved` — число решённых задач, `penalty` — штраф в целых минутах. Больший `solved` имеет приоритет, затем выигрывает меньший штраф. Одинаковые баллы и штраф дают места 1, 1, 3. Для стабильной пагинации внутри ничьей используется UUID.

Формула штрафа принята как проектное решение. В зачёт идёт первая по времени отправки принятая попытка по каждой задаче. Берём число полных минут от старта контеста до неё плюс 20 минут за каждую предшествующую WA, RE, TLE или MLE. Ошибка компиляции, сбой инфраструктуры и попытки по нерешённой задаче дают ноль минут. Например, WA на второй минуте и AC на пятой дают одну задачу и 25 минут.

Кэш Redis хранит результаты 60 секунд. Новый сабмит, зафиксированный вердикт и сброс при rejudge увеличивают версию в той же транзакции PostgreSQL. Старый кэш становится недоступен по новому ключу даже при одновременном пересчёте. Имена загружаются для текущей страницы. При недоступности кэша API считает таблицу из БД.

## Пользователи

- `PATCH /users/me` принимает `{"name":"Степан","avatar_url":"https://example.org/avatar.png"}`. Оба поля необязательны, хотя бы одно должно присутствовать. `"avatar_url": null` снимает аватар. Имя, заданное вручную, сохраняется при следующих входах через GitHub.
- Admin получает список через `GET /users?page=1&size=20`, меняет роль через `PATCH /users/{id}/role` с `{"role":"judge"}` и блокирует через `PATCH /users/{id}/block` с `{"is_blocked":true}`. Для разблокировки передаётся `false`. Изменение и запись в `user_audit` выполняются одной транзакцией.
- Старые JWT учитывают текущую роль. Заблокированный пользователь получает 403 при обращении к приватному API, входе, OAuth-обмене и обновлении сессии. После разблокировки нужен новый вход.
- Первый администратор назначается владельцем развёртывания вручную. Откройте `psql` в контейнере базы:
  ```sh
  docker compose exec db sh -lc 'psql -U "$POSTGRES_USER" -d "$POSTGRES_DB"'
  ```
  и выполните:
  ```sql
  UPDATE users SET role = 'ADMIN' WHERE email = 'owner@example.com';
  ```
  Роль хранится в enum `userrole`, где значения записаны именами в верхнем регистре (`PARTICIPANT`, `JUDGE`, `ADMIN`), хотя API отдаёт их в нижнем регистре. В сыром SQL используйте верхний регистр. Роль читается из БД на каждом запросе, поэтому повторный вход не обязателен. Удалить или заблокировать последнего активного администратора через API нельзя.

## Telegram

1. Получите токен у BotFather. В локальном `.env` заполните `TELEGRAM_BOT_TOKEN`, `TELEGRAM_BOT_USERNAME` (без @) и `TELEGRAM_WEBHOOK_SECRET` (случайное значение, например результат `secrets.token_urlsafe(32)`). Для подключения внешнего Telegram нужен доступный ему HTTPS-адрес backend.
2. Пересоздайте `api` и `notifications` с новыми настройками. Для регистрации webhook выполните команду ниже, подставив свой домен.

   ```powershell
   docker compose up -d --force-recreate api notifications
   docker compose exec api python -m tools.set_telegram_webhook https://YOUR-DOMAIN/api/v1/telegram/webhook
   ```

3. Со своим JWT вызовите `POST /api/v1/telegram/link`. Откройте полученную ссылку и нажмите Start или отправьте боту в личном чате `/start <code>`. Код действует 600 секунд. Подтверждение привязки приходит от бота. Профиль запрашивает `GET /api/v1/telegram/status` с JWT при возвращении на вкладку или по кнопке «Проверить привязку». Ответ содержит `linked`, `linked_at`, отображаемое имя Telegram (`name`) и необязательный `username`. В личном чате команды `/start` и `/profile` показывают привязанный профиль или инструкцию по привязке. Уже привязанному участнику достаточно отправить `/profile` и обновить страницу, чтобы увидеть актуальное имя.
4. Сервис `notifications` совмещает отдельный Celery worker и один периодический планировщик. Запускайте один экземпляр этого сервиса. Каждые 10 секунд он обрабатывает очередь PostgreSQL и наступившие начало/окончание контестов для привязанных на момент события пользователей. При архивации опубликованного, активного или завершённого контеста уже наступившие события сохраняются в той же транзакции.
5. Каждый зафиксированный результат проверки создаёт событие для привязанного участника. При отказе очереди до начала проверки API возвращает 503 и сохраняет вердикт SYSTEM_ERROR вместе с событием. Повторная проверка создаёт новое событие. В `notifications` сохраняются статус, число попыток, результат и время доставки. Telegram 429 учитывает `retry_after`, при сетевых ошибках и 5xx предусмотрено три повтора. Блокировка бота и неизвестный чат снимают привязку. Получатель проверяется повторно перед отправкой.
6. Повтор webhook или повтор планировщика не создаёт второе событие. У внешнего sendMessage остаётся окно повторной доставки, если Telegram принял сообщение, а процесс потерял ответ или завершился до фиксации транзакции.
7. Записи `sent`, `failed` и `cancelled` старше `NOTIFICATION_RETENTION_DAYS` (по умолчанию 30) удаляются ежедневно. Ключи уже учтённых событий контеста сохраняются отдельно, чтобы очистка истории не повторяла рассылку. Ожидающие записи сохраняются.

Для локального стенда на Windows запустите из корня проекта `.\tools\start-telegram.ps1`.
При первом запуске введите authtoken ngrok. После сообщения `Webhook registered.` откройте профиль на сайте.

## Проверка в Swagger

Участником измените имя через `PATCH /users/me` и прочитайте профиль. Тот же JWT для `GET /users` должен дать 403. Администратором проверьте смену роли и блокировку отдельного тестового участника. Для таблицы рейтинга используйте активный контест с задачей. До принятого решения автор отправки имеет 0 решённых задач, после ACCEPTED — 1. Перепроверка принятого решения временно снимает балл и пересчитывает его после нового вердикта.

## Приёмка объединённой ветки

Измерение до публикации дополнений выполнялось на временном Linux-стенде с Python 3.11, PostgreSQL 16 и Redis 6.2. Бенчмарк использовал живой HTTP-сервер, 100 участников и 500 принятых решений. Для 500 чтений прогретого рейтинга при 50 RPS p95 составил 9,24 мс. Для 200 созданий задач при 20 RPS p95 составил 11,97 мс. Эти числа относятся к этому объёму данных и стенду. Команды для воспроизведения на ноутбуке и пороги CI приведены в [README](../README.md).
