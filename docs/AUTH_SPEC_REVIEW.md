# Сверка первого этапа Auth с ТЗ

Этот документ фиксирует состояние на первом этапе разработки. Актуальные настройки, хеширование и проверки описаны в [инструкции запуска](../README.md).


Источник: TECH_SPEC(1).pdf, версия 1.0 от 02.11.2026. Проверена версия
feature/auth, основанная на main 01a24b5, с поправкой auth-stage1-spec.patch.
Это не проверка актуального удалённого PR Judge и не подтверждение готовности
всего проекта. Статусы ниже относятся к этой локальной версии.

## Что подтвердили проверки

- Исходный этап: пользователь прислал лог `30 passed, 1 warning` для unit/API
  и `2 passed` для PostgreSQL. Предупреждение относится к устаревшему импорту
  BlockingPortal в Starlette, а не к падению теста.
- В Swagger подтверждены register 201, login 200 и auth/me 200.
- После поправки по ТЗ в среде подготовки прошли 45 unit/API-тестов на Python 3.11.
- Два обновлённых PostgreSQL-теста требуют повторного локального запуска.
- Число прошедших тестов не подтверждает покрытие >= 70%: coverage не измерялось.
- Существующая схема БД и пользовательские записи поправкой не изменяются.

## Auth и Users

## Последующие PR для варианта №2

1. **Базовая регистрация/JWT/профиль — текущий PR.** Перед открытием применить
   поправку, повторить тесты, явно перечислить отсутствующие функции. Можно
   ревьюить и сливать как промежуточный этап; весь Auth завершённым не считать.
2. **Auth: rate limit и сессии.** Redis-лимит 10 запросов за 60 секунд с IP,
   ответ 429 и Retry-After; access 30 минут, refresh 7 дней, обновление и отзыв.
   Предлагаемая реализация: непрозрачный случайный refresh, хранение его хеша,
   ротация с атомарной проверкой одноразового использования. Сначала определить
   хранилище и поведение при недоступности Redis. Не доверять произвольному
   X-Forwarded-For от клиента: адрес должен приходить через доверенный прокси.
   Refresh должен работать после истечения access, поэтому доступ к нему
   подтверждается действующим refresh, а не только действующим access JWT.
3. **GitHub OAuth.** Регистрация OAuth App, callback, одноразовый state с TTL
   и привязкой к браузерной сессии, обработка отказов и ошибок провайдера.
   Client secret хранится только на сервере. Не объединять существующие
   аккаунты только по совпадению email без безопасного подтверждения связи.
   GitHub access token используется временно для запросов профиля и email.
4. **Users.** Профиль, роли, блокировка и аудит. Добавление полей через
   согласованную с Judge цепочку миграций. Проверить, что заблокированный
   пользователь теряет доступ также с уже выданным JWT.
5. **Contests/Problems/Tests.** CRUD, права Admin/Judge, даты и статусы,
   ограничения времени/памяти. Участнику не отдавать скрытые тесты через API.
   Доступность контеста должна одинаково проверяться в чтении и отправке кода.
6. **Rating.** Решённые задачи, штраф и порядок мест; Redis TTL 60 секунд.
   Нужно согласовать формулу штрафа и правила ничьих, которых в ТЗ нет.
   Инвалидация после фиксации вердикта, включая перепроверку ранее принятого
   решения: один только TTL не обеспечивает немедленное обновление рейтинга.
7. **Telegram.** Одноразовая привязка на 10 минут, проверка секретного заголовка
   webhook, фоновые уведомления с retry. Повтор Celery-задачи не должен
   бесконтрольно дублировать одно уведомление.

Подтверждение email и восстановление пароля в этой версии ТЗ отсутствуют.
Они не являются обязательным следующим этапом. При этом GitHub OAuth и
Telegram имеют средний приоритет в таблицах, но входят в выбранные интеграции
проекта; просто исключать их из итогового результата нельзя.

## Общие границы с Judge/Submissions

| Общий контракт | Решение, которое нужно сохранить при объединении |
|---|---|
| Текущий пользователь | Один get_current_user по Bearer JWT с загрузкой User из БД. X-User-Id не даёт доступ |
| Роли | Общий require_roles; реальные ограничения проверяются API-тестами |
| База | Единые User/Contest/Problem/Test/Submission; одна согласованная цепочка Alembic, без дублирования таблиц |
| Изменение схемы | create_all создаёт отсутствующие таблицы, но не обновляет существующие столбцы |
| Контест | Общие правила времени, статуса и доступа; заранее договориться об UTC |
| Набор тестов | Judge читает те же входы, ожидаемые выходы и лимиты, что сохраняет CRUD |
| Финальный вердикт | Сначала commit БД, затем обновление/инвалидация рейтинга и постановка уведомления |
| Повторная проверка | Учесть ACCEPTED → другой статус, повтор одного события и изменение места |
| Сбой очереди | Запись сабмита и публикация задачи должны иметь стратегию восстановления |
| Общие файлы | Сохранить роутеры auth/users/submissions, настройки JWT/Celery и обе группы зависимостей/тестов |

Работа над feature/auth не требует слияния непроверенного PR Judge. После его
слияния обновить feature/auth из main, разрешить реальные конфликты, повторить
оба набора тестов и сценарий «регистрация → контест/задача → сабмит → вердикт
→ лидерборд → уведомление».

## Несогласованности и пробелы самого ТЗ

- **Хеширование:** FR-AUTH-04 разрешает bcrypt/argon2, NFR-SEC-01 — только
  bcrypt cost >=12. Сейчас выбран Argon2id. Предложение: явно разрешить
  Argon2id в NFR-SEC-01 с документированными параметрами. Это предложение,
  а не уже внесённая правка ТЗ.
- **Роли при отправке:** §2.3 даёт Judge все права Participant, а §5.4 помечает
  POST /submissions только Participant. Нужно зафиксировать ожидаемое поведение.
- **Рейтинг:** нет формулы штрафа, перечня штрафуемых вердиктов, правила ничьих
  и правил повторных ACCEPTED. Для начала можно выбрать ICPC-подобную схему,
  но нельзя выдавать её за уже написанное требование.
- **Лимиты:** NFR-SEC-07 требует 10/мин по IP, FR-SUBMIT-05 описывает лимит
  по пользователю. Это разные проверки; одна не заменяет другую.
- **OAuth:** редирект «с токеном» не определяет способ передачи. До фронтенда
  определить контракт; предложено передавать одноразовый код обмена или
  использовать защищённую cookie вместо access JWT в query-параметре URL.
- **Email:** RFC 5322 охватывает формы, не всегда поддерживаемые EmailStr.
  Нужны примеры допустимых адресов, а не заявление о проверке всего RFC.
- **Контесты:** FR-CONTEST-06 ограничивает участника published/active.
  Решено: guest/participant видят только published/active, finished и archived
  скрыты; история решений остаётся через submissions. Контракт и порядок
  миграций описаны в `docs/CONTESTS_API.md`.
- **Health:** /health сейчас отвечает без обращения к БД/Redis; FR-ADMIN-01
  и NFR-REL-03 требуют проверять обе зависимости. Ответ 200 сам по себе не
  подтверждает их состояние.
- **Нагрузка:** 10 последовательных тестов по 5 секунд могут превышать
  NFR-PERF-04 (30 секунд на сабмит с 10 тестами); уточнить сценарий измерения.
- **Документ:** поля авторов пусты, команда названа «студент + ментор», срок
  «до пятницы» без даты. Введение обещает план тестирования и матрицу
  трассировки, но отдельных таких разделов в приложенном документе нет.
